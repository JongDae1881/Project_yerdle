> 그리고 여기서도 결국 스프링MVC의 DispatcherServlet처럼 서블릿이 하나인 거 아냐?

**프론트 컨트롤러 패턴**은 여러 기능에 대한 요청을 공통 진입점에서 받은 다음, 요청에 맞는 처리 코드로 보내는 방식이다. `3logindao`의 `MainServlet`과 Spring MVC의 `DispatcherServlet`에서 이 역할을 볼 수 있다. [Oracle Front Controller 패턴](https://www.oracle.com/java/technologies/front-controller.html), [Spring MVC DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html)

## 왜 한 진입점에서 요청을 받을까?

상품 목록이나 로그인마다 별도 서블릿을 등록하면 Tomcat이 URL을 기준으로 해당 서블릿을 골라 준다. 여러 기능에 동일한 요청 기록이나 예외 처리 절차가 필요하면 공통 코드가 어느 요청에 어떻게 적용되는지 일관되게 관리해야 한다.

프론트 컨트롤러를 두면 해당 진입점을 지나는 요청에 공통 처리 절차를 적용하고, 기능별 업무는 맞는 처리 코드에 맡길 수 있다. 예를 들어 요청 처리 중 발생한 예외를 공통 규칙에 따라 HTTP 오류 응답으로 바꿀 수 있다. 요청을 한곳에 모은 뒤 처리 기능까지 모두 같은 클래스에 작성하면 분기가 늘어날 때 클래스가 커지므로, 공통 절차와 개별 업무의 위치를 구분하면 관리하기 쉽다. [Oracle Front Controller 패턴](https://www.oracle.com/java/technologies/front-controller.html), [Spring MVC의 공통 처리 구성 요소](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/special-bean-types.html)

## MainServlet과 DispatcherServlet은 어떻게 요청을 분배할까?

요청을 받는 단계와 기능을 고르는 단계가 있다. **Tomcat은 URL 매핑으로 서블릿을 고른다.** 서블릿에 요청이 전달된 뒤에는 **프론트 컨트롤러가 요청에 맞는 처리 코드를 연결한다.** [Jakarta Servlet URL 매핑](https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html#mapping-requests-to-servlets), [Spring MVC의 요청 매핑과 핸들러 호출](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/special-bean-types.html)

| 단계 | SSAFY `3logindao`의 `GET /logindao/main?action=list` | Spring MVC 예시 `GET /rooms` |
| --- | --- | --- |
| 공통 진입점에 전달 | Tomcat이 `/logindao` 앱의 `/main` 매핑으로 `MainServlet`을 고른다. | Tomcat이 등록된 매핑에 따라 `DispatcherServlet`을 고른다. |
| 처리 코드 찾기 | `MainServlet.doGet()`이 요청 파라미터 `action`을 읽는다. `switch`에서 `list` 분기를 고른다. | `DispatcherServlet`이 `HandlerMapping`에 조회한다. 애너테이션 기반 매핑은 `GET` 메서드와 `/rooms` 경로를 보고 `@GetMapping("/rooms")`에 연결된 핸들러를 찾는다. |
| 처리 코드 호출 | `list(request, response)`를 직접 호출한다. | `DispatcherServlet`이 `HandlerAdapter`에 호출을 맡긴다. 어댑터가 인자를 준비해 컨트롤러 메서드를 실행한다. |

`3logindao`의 로그인과 상품 상세 조회도 `MainServlet`의 `action` 분기에 연결되어 있다. Spring MVC 예제에 방 상세 조회를 추가하려면 개발자가 `@GetMapping("/rooms/{id}")` 같은 매핑을 선언한다. Spring MVC는 시작 시 매핑을 등록하고 요청이 올 때 같은 분배 절차에서 사용한다. 구체적인 서블릿 호출과 목록 JSP까지의 흐름은 [[01 · MainServlet과 DispatcherServlet|MainServlet과 DispatcherServlet]]에서 볼 수 있다. [Spring MVC 애너테이션 기반 요청 매핑](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-requestmapping.html)

## 프론트 컨트롤러가 하나면 서블릿도 하나일까?

`3logindao`에서 하나라는 말은 여러 기능 요청을 받는 공통 진입점이 `MainServlet` 하나라는 뜻이다. 같은 앱에도 별도의 URL 패턴으로 다른 서블릿을 등록할 수 있다. JSP 역시 컨테이너에서 서블릿으로 변환되어 실행될 수 있다. 어떤 요청이 프론트 컨트롤러를 지나는지는 그 서블릿에 등록된 URL 패턴이 정한다. [Jakarta Servlet의 등록과 URL 매핑](https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html), [Spring MVC의 DispatcherServlet 등록](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html)

[[04 · MVC|MVC]]는 업무 데이터와 규칙, 화면 표현, 요청 처리 사이의 책임을 나누는 패턴이다. 여기에 프론트 컨트롤러를 함께 쓰면 공통 진입점이 요청을 분배하고, 기능별 컨트롤러가 서비스를 호출해 응답에 쓸 데이터를 준비한다. `DispatcherServlet`과 `RoomController`가 모두 컨트롤러라고 불리는 이유는 각각 요청 분배와 개별 기능의 응답 조정을 맡기 때문이다.
